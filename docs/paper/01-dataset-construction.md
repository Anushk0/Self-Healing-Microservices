## 4.1 Why a purpose-built dataset

Root cause analysis in microservices is usually evaluated on datasets where the fault and the
observable symptom occur on the same service. That framing rewards a system for correctly reporting
*where the alarm is*, which is a weaker capability than reporting *what is wrong*. The dataset
constructed here deliberately makes half its fault types cross-service, so that a system which
simply names the alarming service scores at most 50%.

They were not used directly for one structural reason that should be stated plainly: this project
evaluates a **closed loop** — diagnosis, safety validation, human approval, execution against a live
cluster, and verified recovery. That requires a system that can actually be broken and repaired on
demand, so the incidents must be generated by this project's own fault injectors against its own
running services. A static incident corpus can evaluate diagnosis, but not remediation or recovery.

## 4.2 The monitored system and fault taxonomy

Four Spring Boot microservices (auth, payment, ledger, notification) with a synchronous payment
chain. Four controlled faults, each disabled by default, individually resettable, and exposed
through an HTTP endpoint so injection is scriptable:

| Fault type | Mechanism | Root cause service | Symptom service | Cross-service |
|---|---|---|---|---|
| `auth-key-error` | JWT signing key replaced with a random in-memory key | auth-service | payment-service | **Yes** |
| `memory-leak` | Scheduled task retains `byte[]` chunks without releasing | payment-service | payment-service | No |
| `db-lock` | Raw JDBC connections acquired from HikariCP and held | ledger-service | ledger-service | No |
| `notification-latency` | Fixed sleep before responding to receipt requests | notification-service | payment-service | **Yes** |

The two cross-service cases are not incidental. `auth-key-error` is invisible in auth-service's own
error metrics because `/api/auth/validate` returns HTTP 200 with a `valid: false` body rather than an
error status — verified against live telemetry, where payment-service's error count rose while
auth-service's stayed flat. `notification-latency` surfaces on payment-service because
payment-service awaits the notification call synchronously, bounded by its own client timeout.

## 4.3 Telemetry capture

A Python collector polls each service's `/actuator/health`, `/actuator/prometheus` and
`/fault-status` on a fixed interval, extracting a curated metric schema rather than dumping raw
Prometheus output. It additionally runs a synthetic login-and-payment probe every cycle, which is
necessary rather than decorative: `auth-key-error` and `notification-latency` only manifest on a
real request and are invisible to passive polling. The probe deliberately caches its JWT across
cycles so that a token obtained before an auth-key injection continues to be used — reproducing what
an already-authenticated user would experience.

An experiment orchestrator runs a NORMAL → FAULT_ACTIVE → RECOVERY cycle against a chosen fault,
writing inject/reset event markers, so the four phases can be reconstructed precisely by joining
telemetry against event timestamps.

## 4.4 Incident reconstruction and the incident schema

Each experiment is reconstructed into a single incident record containing: identity and provenance
(`incident_id`, `data_source`, `generation_method`), fault labels (`fault_type`,
`root_cause_service`, `symptom_service`, `affected_services`), phase boundaries, per-service metric
averages for each phase (`baseline_metrics`, `fault_metrics`, `recovery_metrics`), metric deltas,
payment-probe summaries per phase, observed errors, correlation IDs, a heuristic severity label, and
generated natural-language descriptions (`root_cause_description`, `symptom_description`, `summary`,
`postmortem_text`).

`root_cause_service` is the ground-truth label used throughout the evaluation. It is known by
construction — the experiment orchestrator chose which fault to inject — rather than annotated after
the fact.

Two real defects were found and fixed during reconstruction, recorded here because they affected
label quality:

1. **Phase mislabelling on cross-service faults.** The symptom service's own self-reported fault
   flag is always false for cross-service faults, which caused its fault-window telemetry to be
   dropped from `fault_metrics`. Fixed by trusting the self-reported flag only for the actual
   injection target and falling back to the time-window rule elsewhere.
2. **A text-generation operator-precedence bug** that discarded all but the closing sentence of
   postmortem text for same-service faults. Both fixes carry regression tests.

## 4.5 Real and synthetic incidents

Live experiments are time-expensive (each spans a full NORMAL/FAULT/RECOVERY cycle), so the corpus
is topped up with deterministic synthetic incidents to reach an equal count per fault type. The
synthetic generator's fault-phase formulas mirror each real Java fault mechanism — cited by class and
method name in the generator source — and its baseline ranges are anchored to values actually
observed live.

**Provenance is never hidden.** Every incident carries `data_source: "real" | "synthetic"`, that
field is embedded in the postmortem text, and it is stored as retrieval metadata, so a retrieved
incident always announces which kind it is.

> telemetry replaces the synthetic incidents with real ones automatically and requires no code change.

## 4.6 The Memory / Evaluation split and leakage prevention

The corpus is split with a fixed seed, stratified by fault type, into a **Memory set** (20
incidents) used to populate retrieval memory and to train the anomaly detectors, and an
**Evaluation set** (48 incidents) used only for measurement.

This separation is the methodological core of the evaluation: a RAG-based diagnostic system
evaluated on incidents already present in its own retrieval memory measures lookup, not diagnosis.
The separation is therefore enforced in code at four independent points rather than by discipline:

1. **Indexing.** `chroma_store.build_collection()` never opens the Evaluation file; it loads
   Evaluation IDs read-only, refuses to write if any Memory ID overlaps them, and re-verifies by
   direct ID lookup after building.
2. **Detector training.** The training-data loader reads only the Memory file and has no parameter
   that could redirect it, and uses only NORMAL/RECOVERY phases so no detector ever sees a fault
   window.
3. **Feedback write-back.** Completed pipeline runs are written back into retrieval memory, so a
   replayed Evaluation incident could contaminate it. Two independent layers refuse: the writer
   refuses by incident ID before constructing anything, and the store refuses again by source ID,
   refuses any ID lacking the pipeline-run prefix, and **fails closed** when the Evaluation file
   cannot be read.
4. **Evaluation-time verification.** The harness performs a live preflight before recording any
   measurement, attempting a write-back of a real Evaluation incident and aborting the run unless it
   is refused. The reported run's artefact records this check and its result.

Layer 4 exists because the first three are only as good as their last edit. Proving the guard on the
actual Evaluation file at the moment of measurement is a stronger claim than a passing unit test.

## 4.7 Retrieval memory construction

Each Memory-set incident's postmortem text is embedded and indexed with its structured fields as
metadata, so retrieval returns a complete record rather than prose alone. Embeddings use ChromaDB's
bundled local ONNX model — no cloud dependency, and no second model runtime competing with Ollama
for resources.

## 4.8 Threats to validity

- **Synthetic composition (reported run).** See §4.5. The generator's formulas mirror the real fault
  mechanisms and its baselines are anchored to observed values, but modelled faults are smoother than
  live ones; in particular, phase-averaged metrics have lower variance than raw per-cycle telemetry.
  This most plausibly makes anomaly detection *easier* than in production and diagnosis no harder,
  so detection figures from this run should be treated as an upper bound.
- **Scale.** 68 incidents across four fault types is small by machine-learning standards. It is
  adequate for a deterministic-first diagnostic pipeline, whose decision rules do not depend on
  sample size, and inadequate for training a data-hungry detector — which is consistent with the
  detector limitations reported in the Methodology.
- **Fault variety.** Four fault types, each injected by a purpose-built mechanism, cannot represent
  the diversity of production incidents. The claim supported by this dataset is narrow and should be
  stated narrowly: that a deterministic-first, retrieval-augmented pipeline separates root cause from
  symptom on cross-service faults of these kinds better than a single-agent LLM does.
- **Ground truth is by construction.** Labels are known because the injector chose them, which
  removes annotation error but also means the labels cannot capture incidents with genuinely
  ambiguous causes.
